# Architecture

One page, plain language. If you're a new volunteer, read this once and
you should be able to make your first change without asking anyone.

## What this is

A static site (no server, no database, no build step) that shows El Niño
heat and drought risk across Iligan City's 44 barangays. A scheduled job
fetches weather data and writes JSON; the browser reads that JSON directly.
See `CLAUDE.md` at the repo root for the non-negotiable rules (never
fabricate a figure, always label a derived value, etc.) — this doc is about
how the code is organized, not the rules it must follow.

## The pages

| File | What it is |
|---|---|
| `src/index.html` | Overview / hub. The big animated hero, then one card per MVP indicator (real value if live, NO DATA + owning office if not), then the "What We Still Don't Know" reframe. |
| `src/heat.html` | Heat index in depth: today's heat tiers, the city map with the time scrubber, the elevation story. |
| `src/rainfall.html` | Rainfall: 7-day accumulated rainfall and consecutive dry days per barangay, live from `data/rainfall-latest.json`. |
| `src/fire.html` | Fire incidents (official BFP/ICENRO records) stays a data request — but the page also shows a live, separately-labeled NASA FIRMS satellite thermal-anomaly layer from `data/fire-hotspots-latest.json`. The two are never conflated; see CLAUDE.md. |
| `src/exposure.html` | Population exposed by heat band: each barangay's PSA population crossed with its current heat band, live from `data/heat-index-latest.json` + `data/barangays.json`. Recomputes as the scrubber moves; the three mandatory caveats (population dispute, barangay-wide assumption, exposure-not-harm) are always visible. |
| `src/water.html` | Water level/availability + households with water shortage. Two indicators, one page. Not scheduled to go live in the current build plan. |
| `src/agri.html` | Farmers & hectares affected. Not scheduled to go live in the current build plan. |
| `src/response.html` | Government intervention/response status. Not scheduled to go live in the current build plan. |
| `src/ops.html` | Operations console: full 44-barangay table, all charts, the scrubber, the drawer. Built for someone monitoring the whole city at once, not the public. |

Every page that shows barangay-specific data includes the same drawer
markup (`#drawer`, `#drawer-backdrop`, etc.) and calls `initDrawer(...)`
from `src/js/drawer.js`. Pages built purely as "data requests" (water,
agri, response, until their own step ships) don't need the drawer at all;
rainfall.html is live but is a sortable table, fire.html's live satellite
layer is a map without a drawer (events, not barangays, don't have a
barangay detail panel to open), and exposure.html is a population-by-band
split with its own scrubber, not a per-barangay drawer — none of the three
needed the full drawer pattern `heat.html`/`ops.html` use.

## Where data comes from

- `data/barangay_reference_points.json` — the 44 barangays' coordinates,
  PSGC codes, and coordinate provenance/confidence (OpenStreetMap, ODbL 1.0).
- `data/barangays.json` — PSGC codes, names, and PSA population figures
  (including the disputed-vs-2020-census detail exposure.html's caveat
  block quotes directly). Static reference data, not generated by a fetch
  script; `src/js/data.js`'s `computeExposureByBand` crosses it against
  `data/heat-index-latest.json` at read time — there is no
  `data/exposure-latest.json`, since exposure is always a live cross of
  two files already on disk, not something that needs its own fetch.
- `data/heat-index-latest.json` — generated by
  `scripts/fetch/fetch-heat-index.js`. One batched Open-Meteo call for all
  44 points, heat index computed locally via the NWS/Rothfusz formula in
  `scripts/fetch/heat-index.js` (never Open-Meteo's `apparent_temperature`
  — see that file's comments for why). Contains both `records` (the
  schema/record.schema.json-compliant shape) and a richer `barangays` array
  (current reading, today's peak, the full 24-hour curve, elevation) that
  the frontend actually renders from.
- `data/rainfall-latest.json` — generated by
  `scripts/fetch/fetch-rainfall.js`. One batched Open-Meteo call (daily
  `precipitation_sum`/`precipitation_hours`, `past_days=7`) for all 44
  points; the pure math (dry-day threshold, trailing 7-day sum,
  consecutive dry-day streak) lives in `scripts/fetch/rainfall.js` so it's
  unit-testable without a network call. Same two-part shape as heat index:
  schema-compliant `records` plus a richer `barangays` array with the full
  8-day daily breakdown.
- `data/fire-hotspots-latest.json` — generated by
  `scripts/fetch/fetch-fire-hotspots.js`. Streams three NASA FIRMS 7-day
  CSVs (VIIRS aboard Suomi NPP and NOAA-20, plus MODIS — no API key,
  ~5MB each, never buffered whole or committed) and filters to Iligan's
  bounding box as it reads. The parsing/dedup/distance math lives in
  `scripts/fetch/fire-hotspots.js` (unit-testable without a network call):
  great-circle nearest-barangay distance, and deduplication across
  satellites for the same acquisition time within ~500m. Zero hotspots in
  the last 7 days is a valid, expected result, not a fetch failure.
  **These are satellite thermal anomalies, not confirmed fire incidents**
  — `status` is `"reported"`, never `"verified"`, and the official "Fire
  Incidents" indicator stays NO DATA / PENDING regardless of this file.
- Future indicator files follow the same pattern: a Node script under
  `scripts/fetch/` writes one JSON file, validating its own output before
  writing so a bad fetch never overwrites good data.

`.github/workflows/fetch.yml` runs heat index and rainfall hourly and fire
hotspots once daily (fire hotspots don't need hourly re-fetching of three
~5MB CSVs), each indicator its own fetch-then-commit step pair guarded
with `if: always()` — one indicator's hiccup never blocks another's, and
each commit step only commits if that indicator's file actually changed.
`.github/workflows/pages.yml` deploys `src/` + `data/` to GitHub Pages on
every push to `main` (staged as siblings, since GitHub Pages' branch-deploy
source can't serve an arbitrary subfolder as site root).

## Running the fetch locally

```
node scripts/fetch/fetch-heat-index.js
node scripts/fetch/fetch-rainfall.js
node scripts/fetch/fetch-fire-hotspots.js
```

Writes `data/heat-index-latest.json`, `data/rainfall-latest.json`, and
`data/fire-hotspots-latest.json`. No API key needed for any of the three.
Run `node --test "scripts/fetch/*.test.js"` to check the heat index formula
against published NWS values, the rainfall math (dry-day threshold, 7-day
sum, consecutive dry-day streak), and the fire-hotspot math (bounding box,
great-circle nearest-barangay distance, cross-satellite dedup, the
zero-filled daily timeline) against hand-worked examples.

## Previewing the site locally

`data/` must be a **sibling** of the HTML files, not one level above —
that's how the GitHub Pages deploy stages it, and every page's fetch calls
(e.g. `fetch('data/heat-index-latest.json')`) are relative paths that
assume that layout. To preview locally:

```
mkdir -p _site && cp -r src/. _site/ && cp -r data _site/data
npx --yes serve _site
```

(`_site/` is git-ignored — it's a local preview convenience, not a repo
artifact.)

## The shared modules (`src/js/`)

Every page is a thin HTML shell + a small page-specific script that
imports what it needs. Nothing below is duplicated per page — if you find
a literal band threshold, a band hex color, or a repeated date-formatting
function outside `data.js`, that's a bug, not a style choice.

- **`data.js`** — the single source of truth. Band thresholds (Celsius,
  matching `scripts/fetch/heat-index.js`'s NWS/Rothfusz `band()`
  function), band CSS classes, Manila time formatting, the tie-safe
  competition-ranking function, number-tween animation, and
  `loadDashboardData()` (the one place every page fetches from).
- **`charts.js`** — every Chart.js chart the site draws, plus the inline
  SVG sparkline (not Chart.js, but still "a chart"). Reads theme colors
  fresh on every call via `chartTheme()`, so a theme toggle just needs a
  re-render, not new logic.
- **`map.js`** — Leaflet setup. `createBaseMap()` bakes in two fixes worth
  knowing about if you touch it: `zoomSnap: 0.1` (Leaflet's default
  `zoomSnap: 1` rounds fitBounds down to the nearest whole zoom level,
  which for Iligan's oddly-shaped 44-point bounding box wasted up to a
  full zoom level and rendered the city tiny in the middle of three
  neighboring provinces), and `setMaxBounds()` so panning can't wander
  into them. Dark tiles come from a CSS `invert()` filter on plain
  OpenStreetMap tiles, not a "dark basemap" provider — CARTO's and
  Stadia's free dark tiles both now require an API key tied to one
  person's account, which conflicts with this project's "no dependency on
  one person's account" rule.
- **`drawer.js`** — the barangay detail panel. Page-agnostic: call
  `initDrawer(data, referenceData)` once, then `openDrawer(name)` from
  anywhere. Supports deep links: `initDrawer` reads `#brgy=<psgc_code_9>`
  on load via `openFromHash()`, and `openDrawer`/`closeDrawer` keep the
  hash in sync (via `history.replaceState`, so it never spams browser
  history).
- **`scrubber.js`** — the 24-hour time control. Knows nothing about
  charts or maps — it just manages play/pause/keyboard/the range input
  and publishes a `window` `"hourchange"` `CustomEvent` with the new hour
  index. Any page that cares listens for that event and updates whatever
  it owns.
- **`chrome.js`** — theme toggle (dark is the default for a first-time
  visitor; a stored choice always wins over the system preference), the
  freshness chip, the peak-countdown chip, the footer timestamp, the
  shared inline SVG icon set, the shared nav (`NAV_ITEMS` + `renderNav`),
  and `initScrollReveal` (the fade/slide-in on scroll every page with
  `.reveal` sections uses — one `IntersectionObserver` threshold defined
  once, not re-declared per page).
- **`pending-boot.js`** — the few lines every remaining "data request" page
  shares (nav, theme toggle, the freshness/last-updated footer text). Not
  one of the core modules above, just avoiding repeating the same lines
  once per pending page. A page drops this the same step it goes live
  (see `rainfall.js` for what replaces it).

## How to add an indicator

1. If the indicator needs its own external data, write
   `scripts/fetch/fetch-<indicator>.js`. Validate the output (right record
   count or structure, no null/NaN values) before writing the JSON file —
   see `fetch-heat-index.js`, `fetch-rainfall.js`, or
   `fetch-fire-hotspots.js` for the pattern. If the indicator needs any
   non-trivial math, put it in a separate pure module (`rainfall.js`
   alongside `fetch-rainfall.js`, `fire-hotspots.js` alongside
   `fetch-fire-hotspots.js`) so it's unit-testable without a network call.
   Never invent a figure; unknown stays `null`. A valid "nothing happened"
   result (zero rows, zero hotspots) is not a validation failure — don't
   conflate "no data because it's broken" with "no data because that's the
   honest answer this week." Not every indicator needs a fetch script at
   all: population exposed has no `fetch-exposure.js` or
   `exposure-latest.json` because it's a pure cross of two files already
   on disk (`heat-index-latest.json` × `barangays.json`) computed at read
   time by `computeExposureByBand` in `data.js` — write a fetch script
   only when there's actually new external data to go get.
2. If the indicator has its own page already (e.g. `water.html`,
   `agri.html`, `response.html`), replace its "data request" content with
   the real page: real numbers, the real "last updated", and the required
   labels (`status`, `source`, the derived-indicator sentence if it's a
   derived value — see `CLAUDE.md`). A supplementary layer that doesn't
   actually fill the named MVP indicator (NASA FIRMS hotspots on
   `fire.html` are satellite detections, not the "Fire Incidents" indicator
   itself) goes live on the page alongside the still-pending "data
   request" content, not in place of it — see `fire.html`/`fire.js`. If the
   indicator crosses two pillars and needs mandatory caveats to stay
   honest (population exposed crosses Environmental heat data with Social
   population data, and carries three: the population-baseline dispute,
   the barangay-wide-exposure assumption, and "exposure is not harm" — see
   `exposure.html`), those caveats must stay visible everywhere the number
   appears — on `exposure.html` they're static markup that's always on
   the page (not
   something JS renders or could accidentally skip), so moving the
   scrubber recomputes the number but can never hide the caveats sitting
   right next to it.
3. Update `src/overview.js`'s indicator card for that indicator to show
   the real value — but only if this step's data actually fills that named
   MVP indicator. Fire hotspots don't fill "Fire Incidents" (see step 2),
   so the Overview card and the "What We Still Don't Know" reframe
   correctly keep listing it NO DATA / PENDING;
   don't "fix" that. Don't speculatively fetch a file before it exists
   "just in case" — a 404 gets logged to the console by the browser itself
   no matter how gracefully your JS catches
   it, so every indicator card is hardcoded NO DATA until its own step
   actually ships the file.
4. Remove `pending: true` from that page's entry in `chrome.js`'s
   `NAV_ITEMS` so its nav link stops showing the pending dot.
5. If the indicator should appear in the ops-view table/charts, extend
   `src/ops.js`. If it needs its own band thresholds or color, they go in
   `data.js`, not inline in the new code.

## What must never be hardcoded

- A band threshold or a band's hex color anywhere outside `data.js`.
- A barangay coordinate, a population figure, or any other precise value
  guessed rather than sourced — see `CLAUDE.md`'s non-negotiables.
- A "last updated" timestamp not derived from the actual data file's
  `generated_at`.
- A page assuming which other page it was opened from — `drawer.js`,
  `scrubber.js` and `map.js` must keep working with no knowledge of which
  HTML file loaded them.
